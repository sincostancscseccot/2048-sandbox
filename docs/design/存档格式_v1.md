# 2048 Sandbox 存档格式 v1

**日期：** 2026 年 10 月 14 日  
**状态：** 应用 v0.6.0 / M4 继续使用格式 v1，新增能力和多规则版本闭包。本文记录实际实现，原 [格式草案](存档格式草案.md)保留为设计依据。

M5 / 应用 v0.7.0 继续使用相同容器和能力。新增的 2048-sandbox-path-statistics JSON 是独立分析报告，供查看或外部处理，不走游戏恢复通道；内容与口径见 [M5 操作说明](交互与统计_M5.md)。

## 1 文件范围

| 文件 | 内容 | 导入行为 |
|---|---|---|
| 规则 .json | 完整经典或已支持的自定义规则 | 预览后按规则创建新对局 |
| .2048state | 选定节点与完整恢复依赖 | 导入为独立副本，打开选定节点 |
| .2048lab，branch | 根到选定节点的路径与恢复依赖 | 不含无关分支，仍可继续 |
| .2048lab，project | 一个对局的全部节点、检查点、归档和设置 | 导入完整独立副本 |
| .2048backup | 多个对局及其全部依赖 | 一笔事务导入整个库的副本 |

除规则 JSON 外，其余文件均使用标准 ZIP，默认 DEFLATE。读取按文件内容识别，不信任扩展名。完整备份含归档分支；节点/路径导出明确显示局部范围，不能冒充整库备份。

## 2 容器布局

单项目使用：

```text
manifest.json
project.json
nodes/<project-id>/index.json
nodes/<project-id>/part-000001.jsonl
rules/<rule-id>/<version>.json
states/<state-sha256-hex>.json
deltas/<result-state-sha256-hex>.json
```

项目库将项目文件和 nodes/ 放在 projects/<project-id>/ 下。rules/、states/、deltas/ 是容器内共享的内容地址池；没有嵌套 ZIP，多个项目可共享同一份完整状态。

project.json 包含 record 和 checkpoints。record 包含核心 Project、更新时间、可选 archivedRootIds 与导入来源。节点 JSONL 每段不超过 512 个；索引记录所属项目、节点总数和每段路径/数量。

完整快照内容是 GameState。快照地址始终为规范化完整状态的 SHA-256；增量条目的字节摘要与还原状态的摘要分开验证。

## 3 清单与摘要

manifest 包含 format=2048-sandbox、formatVersion=1、exportKind、exportedAt、requiredCapabilities、entryCount、nodeCount、stateCount、projects、states、entries 和 settings。

- entryCount 为 entries 的数量，不包含 manifest 本身；ZIP 实际条目数为 entryCount + 1。
- entries 记录每个有效载荷的路径、类型、解压字节数和原始字节 SHA-256；不包含清单自己的摘要。
- projects 记录源项目 ID、项目文档/节点索引路径、根节点和选定节点。
- states 记录完整状态 hash、条目路径、full/delta 编码和可空 baseHash。
- settings 当前保存最后活跃项目；导入时映射到副本项目 ID。

JSON 输出按现有契约规范化：ASCII 字段名排序、UTF-8、无额外空白，精确整数使用十进制字符串。JSONL 每行独立规范化。导入同时验证 ZIP 头/CRC、原始条目 SHA-256、完整状态摘要、结构、引用和节点回放；CRC 不能代替 SHA-256。

机器可读结构见 [archive-v1.schema.json](../../schemas/archive-v1.schema.json)与[核心契约](../../schemas/contracts-v1.schema.json)。Schema 以外的关系和预算由读取器校验。

## 4 完整快照与增量

默认根、检查点、撤销、rule-edit、携带 nextRuleRef 的棋盘编辑和每 32 步边界保存完整快照；其余节点在增量更小、基础已纳入闭包时采用 deltaVersion=1。导出界面也可选择全部完整快照。无论表示方式，恢复后的状态摘要完全相同。

增量包含 baseStateHash、resultStateHash、patches。patches 只支持已有字段/数组元素 replace 和数组尾部 add，使用字段段数组表示路径；不支持删除、任意宿主代码或危险原型路径。解析后重新执行完整状态校验与结果哈希检查。

输出的连续增量不超过 31 份；读取器最多接受 32 份，拒绝循环、缺少基础、未知版本和超过预算的链。共享检查点状态强制使用完整快照，即使另一个节点先引用它。

本地 IndexedDB 仍保存完整状态，增量用于可携带文件；本地和文件都以内容哈希去重。节点身份与快照身份始终分开。

## 5 闭包与一致视图

导出先在同一只读事务读取完整一致视图，再选择项目或节点。局部导出递归纳入父链、undoStack、undoTargetId、规则和快照依赖，保留引用到的检查点和归档标记；其 activeNodeId 为选定节点。

同一对局允许多个规则版本：对所有纳入的状态收集 ruleRef，导出对应规则池；不只导出活跃节点的最新规则。规则 JSON 单独导出所选对局活跃节点的规则。恢复时，每个父/子状态按自己的规则执行；更换规则必须有相符的 edit.nextRuleRef 或 rule-edit 发布动作。

压缩、摘要和解压自检在数据库事务之外完成。超过当前输出限制时不生成一个应用自身无法恢复的文件。导出不修改项目 revision、成绩、操作数或随机状态。

## 6 导入副本与命名空间

读取和验证完成后先显示范围、对局数、节点数、状态数、检查点、体积和迁移说明。用户点击导入后，整个批次在一个写事务中提交。空间不足、规则冲突或写入异常会回滚全部副本；重试沿用同一批次和副本 ID。

导入映射项目 ID，检查点使用新的本地 ID；**节点 ID、父节点 ID、动作、时间、undoStack、随机流、成绩和完整状态摘要保持原值**。节点的 matchId 映射到新项目，数据库使用 (matchId, nodeId) 作为身份，operationId 也在项目内唯一。因此重复导入可以保留原始状态摘要，同时不会混合两份历史。

每份副本保存 sourceProjectId、sourceHash、sourceFormat、importedAt 和 batchId。现有同 ID 项目不被覆盖；当前不提供把文件合并进既有项目的模式。

## 7 资源与格式边界

| 边界 | v1 实现 |
|---|---|
| 压缩文件 | 最多 64 MiB |
| 解压总量 | 最多 256 MiB |
| 单条目 / 旧 JSON 文件 | 最多 32 MiB |
| ZIP 条目 | 最多 50000，包含清单 |
| 单条目实际压缩比 | 最多 200 |
| 路径 | 最多 240 个 ASCII 字符，相对路径 |
| JSON | 最大深度 64、每次解析最多 2000000 个值 |
| 增量路径 / 补丁 | 最深 32 段，最多 4096 条补丁 |
| ZIP 编码 | STORE / DEFLATE；暂不支持 ZIP64、分卷和加密 |

这些是拒绝上限，不是已达到的设备性能承诺。相较原草案，M2 对压缩文件和普通 ZIP 条目数使用更保守的边界。

解压前交叉核对目录与本地头、路径、尺寸和压缩方式；随后按 16 KiB 压缩输入分块解压并限制实际输出。拒绝重复路径、绝对路径、盘符、反斜杠、空段、点段、NUL、符号链接、重叠数据、额外本地条目和嵌套容器。清单必须完整覆盖实际文件，不接受未列出的额外条目。

未知能力在预览前给出具体名称并拒绝写入。M4 支持 core-v1、sandbox-v1、skills-v1、editing-v1、advanced-v1、events-v1；清单必须覆盖所有规则能力。编辑需要 editing-v1，高级合并/数列/生成需要 advanced-v1，事件或变量需要 events-v1。实际规则按 ruleRef 读取，同一对局与混合项目库均可包含不同版本。尚未提供未知规则的只读导入；资源不会触发网络加载。

## 8 兼容与升级

- M1 的 2048-sandbox-m1-backup / schemaVersion=1 JSON 可导入，作为完整快照库迁移；原文件不修改，原节点与状态摘要不变。
- M1 IndexedDB v1 自动经过 v2 复制节点表、v3 移除旧表，转换为项目命名空间并增加导入批次记录。升级在数据库事务中进行，保留项目头、状态、规则、检查点和设置。
- 容器、状态、规则、PCG 和增量分别有版本。无可用迁移器的未知版本拒绝，不猜测缺失字段，不自动修复损坏摘要。
- M3 数据库仍为 v3，不修改 M2 表结构或既有节点；旧文件继续可读。旧 M2 应用不具备 sandbox-v1 / skills-v1，无法执行 M3 自定义文件。
- M4 数据库仍为 v3，容器和核心 Schema 版本保持 1；扩展严格结构并以能力标识控制执行。旧规则、无事件世界的字段形状和已有状态摘要保持不变。旧应用不支持 editing-v1 / advanced-v1 / events-v1 时必须拒绝新文件，不能忽略能力运行。
- 升级后请刷新其他仍运行旧应用代码的页签；当前验证覆盖迁移和同版本多页写入，未承诺新旧应用长期混用。
