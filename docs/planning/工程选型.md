# 2048 Sandbox 工程选型

**日期：** 2026 年 10 月 14 日  
**状态：** M1–M5 的实际依赖已精确锁定，类型检查、161 项单元测试、36 条浏览器流程和生产构建通过。M5 沿用现有依赖，提供精确统计与只读状态展示，使用 SVG 树/图表、自有视口索引和 Canvas 总览；React Flow/Dagre 仍仅为后续候选。

## 1 推荐方案

建议采用 **TypeScript + React + Vite 的离线 Web 应用**。纯规则引擎与界面分开；本地事务存储使用 IndexedDB / Dexie，规则与存档结构使用 JSON Schema，PWA 缓存应用资源，ZIP 负责可携带文件。这个选择依据是本项目的可恢复状态、复杂设置和历史树需求；首版不需要在线服务。

Vite 提供 React 与 TypeScript 项目入口和静态构建能力；React 的组件与状态组织适合拆分设置、棋盘和节点详情。这是结合项目要求的工程判断，并非这些工具保证游戏逻辑正确。[Vite 文档](https://vite.dev/guide/)、[React 文档](https://react.dev/learn/thinking-in-react)。

## 3 关键取舍

### 3.1 独立引擎

引擎只接收规则版本、完整状态、动作、显式随机输入与逻辑时间，返回候选结果。类型放在 domain，结算放在 engine，不能从 React 组件内部保存技能余量或分数。M1 先用主线程纯函数；事件和大树处理达到可观负载时再转 Worker，不先引入工作线程通信复杂度。

数值用 BigInt，序列化为 IntText。首版使用固定版本的 PCG32 随机适配器；算法与数据契约一起版本化，不调用 Math.random 决定游戏结果。

### 3.2 本地存储

采用 IndexedDB，Dexie 用于事务和版本迁移。状态对象、节点、规则、operationId 索引和项目头在同一读写事务内更新。摘要、压缩与其他外部异步任务必须先完成，避免 IndexedDB 事务过早结束；这一限制由 [Dexie 事务文档](https://dexie.org/docs/Dexie/Dexie.transaction())明确说明。

M1/M2 的本地数据库按 SHA-256 去重完整状态，节点不合并。M2 在可携带文件中使用定期完整快照、检查点完整快照、有界增量和无损压缩；本地恢复仍直接读取完整状态。历史节点和 operationId 按项目隔离，使重复导入能保持节点 ID 与状态摘要。数据库只是本地副本，显式文件备份是数据所有权的一部分。配额异常整批回滚和完整库恢复已验证。[浏览器存储说明](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)。

### 3.3 离线与更新

PWA 缓存版本化的应用资源，用户对局存于数据库。首次获取并完成缓存后才能承诺离线打开；不能把 `file://` 双击与正式 PWA 运行混为一谈。正式本地调试使用 localhost，公开部署使用 HTTPS。

更新采用提示后刷新：等待当前操作保存完成，再允许切换版本，不在对局中强制刷新。插件的提示更新模式可提供相应入口。[Vite PWA 更新文档](https://vite-pwa-org.netlify.app/guide/prompt-for-update)。

### 3.4 时间树

M1 使用节点列表完成恢复。M2 已实现自有 SVG 画布、迭代布局和视口筛选，支持缩放、平移、折叠、查找、归档与只读回放；继续保留节点列表。领域树保持自有不可变节点结构，画布布局不进入存档。

纯布局测试覆盖深度 10000 的路径，浏览器覆盖实际多分支交互；完整应用的大规模恢复、布局、导出和内存占用仍需测量。React Flow/Dagre 保留为候选，其减少重绘与折叠建议可参考 [React Flow 性能文档](https://reactflow.dev/learn/advanced-use/performance)。后续按测量结果评估分页、聚合或 Canvas。

### 3.5 校验与文件

使用 JSON Schema draft 2020-12 与 Ajv2020，开发期结构校验和运行期导入共用 Schema。引用完整性、树结构、摘要、精确数值和技能资源需要额外语义校验；不能依赖 Schema 独立完成。[Ajv JSON Schema 文档](https://ajv.js.org/json-schema.html)。

M2 已使用 fflate 0.8.3 完成 ZIP / DEFLATE。解压前检查 ZIP 目录与本地头，解压时按 16 KiB 输入块执行实际输出预算，随后校验 CRC、清单、SHA-256、引用、增量及随机回放。独立 Python zipfile 互操作和恶意输入测试已通过；实际限制见 [存档格式 v1](../design/存档格式_v1.md)。压缩实现参考 [fflate 项目](https://github.com/101arrowz/fflate)。

## 4 工程边界

沿用实施计划的 domain、engine、random、history、persistence、presets、ui、app 划分。暂采用单包工程，避免在首个游戏中引入多包发布与依赖循环。

UI 使用局部状态和小型应用协调层；没有实际状态共享压力时不额外引入全局状态库。基础样式使用 CSS 变量和响应式布局，棋盘用 CSS Grid。历史摘要通过受控查询读取，不能每次移动都重绘整棵树。

## 5 M1 工程骨架的落地顺序

1. 建立 package.json、精确依赖和 lockfile，开启严格类型检查；先核对 peer 和浏览器资产。
2. 引入当前 Schema、经典预设和契约样例，冻结引擎输入输出接口。
3. 实现方向移动、单次合并、分数、生成和胜负，测试典型顺序与边界。
4. 实现完整状态、节点成绩、事务保存、幂等操作与异常恢复。
5. 完成正常游戏页、基础节点列表、检查点和恢复入口。
6. 增加 PWA 资源缓存与离线重开验证，完成 M1 验收后再进入 M2。

建议脚本为 dev、typecheck、test、test:e2e、build、preview。Vite 的转译不替代完整类型检查；构建门槛包含独立类型检查、规则测试和实际浏览器恢复流程。[Vite TypeScript 说明](https://vite.dev/guide/features.html#typescript)。
